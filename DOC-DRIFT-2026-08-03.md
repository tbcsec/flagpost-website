## P1 — functional gaps. An operator following current docs gets a wrong result.

### 1. SMTP password is now excluded from the platform backup (#109, `8af20e7`)

**What changed.** `SiteSettings.smtp_password` became an `EncryptedString` column
(ADR-0020's facility, already used for the OIDC client secret) and is now
**deferred**, so ordinary settings loads never decrypt it — deliberate, because
`EncryptedString` raises on a key mismatch and that row is read on the public
pre-auth branding path *and* on the admin settings page an operator would need to
recover from a lost key. The mailer undefers it at the one point of use.

Migration `e7c1f9a4b206` encrypts the single pre-existing plaintext value on
upgrade, decrypts on downgrade, and is idempotent via the `gAAAAA` Fernet prefix.
The underlying column stays `TEXT`, so there is no schema change.

**The documentation-critical part:** the backup export now drops the column via a
new per-column `Spec.secret_columns`. This is load-bearing rather than cosmetic —
the export reads through the ORM, which *decrypts*, so without the drop a backup
would have shipped the SMTP password in plaintext.

**Why it must be documented.** A restored install will silently fail to send mail
until an operator re-enters the SMTP password. Nothing surfaces that; outbound
email just stops. `admin/backup.md` currently lists what's deliberately excluded
("active login sessions, in-app notifications, collaborative-note snapshots,
personal dashboard layouts, division memberships") and the SMTP password is not
among them.

**Where it belongs.**
- `docs/src/content/docs/admin/backup.md` — add the SMTP password to the
  "Deliberately excluded" paragraph, and add a restore-time step: *re-enter SMTP
  credentials after importing `site_settings`*. Same posture as the already-excluded
  OIDC provider secret.
- `docs/src/content/docs/deploy/security.md` — the bullet at ~L40 currently reads
  "provider secrets are stored encrypted (ADR-0020)". Broaden it: the SMTP password
  is now encrypted at rest too, and the plaintext-recoverable-secret set is closed.
- `docs/src/content/docs/deploy/upgrades.md` — note the one-shot migration and that
  it is reversible on downgrade.
- `docs/src/content/docs/admin/site-settings.md` — SMTP section: the password is
  write-only over the API (`GET` exposes only `smtp_password_set`) and is not
  carried in backups.
- Consider a short **key-rotation** procedure lifted from ADR-0020 (stop, swap the
  key, re-enter both secrets). Zero-downtime rotation was deliberately not built.

### 2. SSO now honours the registration toggle and the email-domain allowlist (#118, `1359653`)

**What changed.** `resolve_identity` applies the site admission policy immediately
before JIT provisioning:

- Registration closed → rejected with `registration_closed`.
- Allowlist enabled and the address is not a **verified** member of an allowed
  domain → rejected with `domain_not_allowed`.

Both raise `IdentityRejected` and land on `/login?error=<code>`, deliberately
without disclosing whether a local account exists for the address.

The gate applies to **step 3 only**. An already-linked external identity (step 1)
and a link onto a pre-existing local account (step 2) both return before it, so no
existing user is locked out and admin-created accounts are unaffected — matching
#56's own carve-out.

Folded in is a genuine security fix: `email_verified` was read with `bool()`, so
the string `"false"` — a serialisation OIDC Core §5.1 permits and several providers
emit — coerced to `True`, marking every user verified. It is now parsed strictly at
both the id_token and userinfo sites.

**Why it must be documented.** This inverts an operator's mental model. Before,
enabling a public provider (Google, GitHub) let *any* account there JIT-provision a
Participant, regardless of the allowlist — the docs describe the allowlist as
governing registration, which was true and is now true of more paths. Two operator-
visible consequences follow: federating to a specific Workspace/Entra tenant now
actually works via the platform allowlist, and **turning registration off now also
blocks new SSO sign-ups** (existing users keep working). Someone who closes
registration mid-event without knowing this will lock out latecomers.

**Where it belongs.**
- `docs/src/content/docs/admin/sso.md` — a new "Who may sign in" section: the
  admission gate, which of the three resolution steps it applies to, the two
  rejection codes and how they present on the login page, and the requirement that
  the address be *verified* (the domain gate is only as good as `email_verified`).
- `docs/src/content/docs/admin/site-settings.md` — the registration-open and
  allowlist controls now have SSO reach; cross-link to `sso.md`.
- `docs/src/content/docs/deploy/security.md` — extend the SSO bullet.

## P2 — new public surface, entirely undocumented

### 3. Venue / projector mode (#77, `b47f9ee`)

The largest feature in the batch and the most visible one. A full-screen,
unauthenticated big-screen display for in-person events.

**Frontend.** Toggled in-page from the existing `/public/[competitionId]` spectator
view via `?venue=1` — bookmarkable and refresh-safe, which matters for an unattended
display. It auto-rotates three widgets (scoreboard, insights, points timeline) on a
15s cadence, overridable with `?interval=`. A first-blood takeover overlay fires on
new first bloods. Operator controls: fullscreen button, arrow keys to step, space to
pause, Esc to exit.

**Backend.** One new read-only public endpoint:

```
GET /api/public/competitions/{competition_id}/activity
→ PublicActivityOut { recent_solves: RecentSolveOut[] }
  RecentSolveOut { challenge_id, title, subject_name, solved_at, points, is_first_blood }
```

Freeze-aware and under the same opt-in / archived gating as the board it
accompanies, so a frozen competition emits no post-cutoff solves and therefore no
splash. The first-blood definition was refactored into one shared helper so the feed
and the insights leaderboard cannot disagree. Polling only — no WebSocket, hence no
ADR.

**New config key:** `public_activity_cache_seconds` (default `5.0`) — a shorter TTL
than the insights memo because venue mode polls faster; `0` disables.

**No new competition column.** Venue mode is implied by the existing
`public_scoreboard` opt-in, so there is nothing for an organiser to enable beyond
what they already do for the spectator board. That is worth stating explicitly — it
is the first question anyone will ask.

**Why it must be documented.** It is a headline v1.3.0 feature adding an
unauthenticated API surface, and the current docs are now actively *understating*
the product: `guides/scoreboard.md` L55 describes the public board as being "for
projectors and spectators" while documenting only the static page, and the apex FAQ
says "There is a public spectator board for projectors". Both now sell short a
purpose-built venue mode.

**Where it belongs.**
- `docs/src/content/docs/guides/scoreboard.md` — a new "Venue / projector mode"
  subsection under "Public spectator board" (the section starts L52): the `?venue=1`
  URL, the three rotating widgets, `?interval=`, the keyboard/fullscreen controls,
  the first-blood splash, freeze behaviour, and the no-extra-opt-in point.
- `docs/src/content/docs/reference/api.md` — add a row to the public-endpoints table
  (currently L78–81) for `GET /api/public/competitions/{id}/activity`, noting
  freeze-parity with the board.
- `docs/src/content/docs/deploy/configuration.md` — `public_activity_cache_seconds`.
  Note that `public_insights_cache_seconds` is *also* currently undocumented; either
  document both or neither, but they should be consistent.
- **Apex** — this deserves promotion, not just a doc entry. In-person venue display
  is a real differentiator against other platforms: worth a `Features.astro` bullet
  and a `Comparison.astro` row, and the `faq.ts` real-time answer (L40) should be
  updated so it no longer describes the weaker capability.

## P3 — user-visible behaviour the docs don't mention

### 4. Logo upload is validated by magic bytes (#114, `2587f58`)

The upload previously trusted the client's `Content-Type` and stored it, so a
renamed non-image with a spoofed `image/png` header passed — and that unverified
type was then what the file was served back as, making the `nosniff` header on the
download path guard a type nobody had checked.

The client header is now discarded and the type derived from the bytes.
`sniff_logo_type` accepts PNG, JPEG, WebP, GIF (by magic bytes) and SVG
(structurally: the payload must decode as UTF-8 and its first element, after any
BOM / XML prolog / DOCTYPE / comments, must be the `<svg>` root). The existing
pixel-budget guard now also applies to raster logos.

Two honest caveats the docs should carry: a well-formed `<svg>` carrying a
`<script>` still passes the sniff — residual risk contained by the serve path's
sandbox + `nosniff` CSP and the fact that the logo renders only via `<img src>` —
and the prolog scan was reworked to a single linear pass after review caught an
O(n²) ReDoS (a 1 MB logo of tiny leading comments cost ~4.8s of event-loop time;
now ~24ms).

**Where:** `docs/src/content/docs/admin/site-settings.md`, branding/logo section —
accepted formats, the 1 MB cap, and that a mislabelled file is now rejected with
415, an over-large raster with 413. Optionally a line in `deploy/security.md` on
upload handling.

**Why:** an admin whose previously-working logo upload starts failing has no way to
diagnose it from the current docs.

### 5. Challenges: grouped list view (#55, `d64cfa5`)

An opt-in "list" presentation on the challenges browse page, selectable via a
Cards/List toggle. The card grid remains the default. List view groups challenges by
category into collapsible sections — collapsed by default — each row a compact line
of name, difficulty, solve count and points, with a padlock on locked challenges and
a soft tint on solved ones. Both views consume the same filtered set, so category
and availability filters behave identically. No backend or API change.

The preference is **per-device, not per-account** — `localStorage` keys
`fp:challenges-view` and `fp:challenges-expanded`. That distinction is exactly the
sort of thing that generates support questions ("why is my view different on my
laptop?"), so it is worth one explicit sentence.

**Where:** `docs/src/content/docs/guides/challenges.md` — a short "Browsing: cards or
list" subsection.

### 6. ADR-0022 accepted — SAML and LDAP provider model (`8f4b653`, `64f4c10`)

Accepted 2026-08-02. It replaces `oidc_providers` with a site-wide
`identity_providers` table discriminated by `kind` (`oidc` | `saml` | `ldap`), with
one `EncryptedString` `secret` column and a `config` JSON column validated by a
Pydantic discriminated union. The migration repoints
`user_external_identities.provider_id`, copying the secret as a raw SQL column value
rather than through the ORM. Notably, `resolve_identity` is **not** reused unchanged:
OIDC's `email_verified` trust model does not transfer to a SAML `NameID` (often no
email at all) or an LDAP bind (proves credential control, not `mail` ownership), so
the trust model becomes per-provider.

**Where:**
- `docs/src/content/docs/dev/adrs.md` — the ADR index is a documented surface and is
  now incomplete; add 0022.
- `docs/src/content/docs/admin/sso.md` — a forward-looking note is worthwhile for
  anyone scripting against provider configuration, since `oidc_providers` is slated
  to be replaced.
- **Apex** `Roadmap.astro` — the "More authentication modules" entry (L29–31) is
  still accurate but can be sharpened: the design is now accepted and both issues are
  plan-ready in the v1.3.0 milestone.

## P4 — minor, cheap to fold into the above

### 7. Profile page is now tabbed (#113, `cb8e6e2`)

Account · Notifications · API tokens. Frontend-only. Any doc text that directs a
user to "/profile" for API tokens (see `admin/users-roles.md` and `reference/api.md`)
should name the **API tokens tab** so the instruction still matches what's on screen.

### 8. Setup drift guard (#133, `f2855e8`; #132, `b7c846d`)

`setup_completed_at` now has a single writer, `auth.setup.mark_setup_complete` —
an atomic conditional UPDATE that preserves the wizard's race guard (the concurrent
loser still gets a 409) and is shared by the wizard, `seed_admin_user` and
`seed_demo_data`. A startup consistency net warns loudly if an active global
Administrator exists but setup was never marked complete; it warns rather than
self-heals, because the wizard correctly refusing points at the real bug.

**Where:** `docs/src/content/docs/admin/setup.md` or `deploy/production.md`
troubleshooting — what that warning means and that a refusing wizard is correct
behaviour, not a fault. Low priority, but it is a log line operators will paste into
a search box.
