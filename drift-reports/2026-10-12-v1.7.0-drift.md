# P0 — Object storage: RustFS replaces MinIO (ADR-0041, #426)

## What changed

MinIO withdrew its open-source edition: the upstream repo is archived (no
releases, no security patches) and on ~2026-09-11 the `minio/minio` and
`minio/mc` repositories were **removed from Docker Hub entirely** (the
repository answers 404; the quay.io copy is not anonymously pullable). Every
Flagpost compose stack pulled `minio/minio:latest`, so **any fresh
`docker compose up` fails**, and the public demo's hourly reset silently
stopped for a month because its `compose pull` could no longer succeed.

The fix (`6251203`):

- **Server:** `rustfs/rustfs:1.0.1`, pinned, Apache-2.0, amd64+arm64, with
  `ghcr.io/rustfs/rustfs:1.0.1` documented as a mirror. Two registries at one
  pinned tag is the direct lesson of the removal. Compose service `minio` →
  `rustfs`; volume `minio-data` → `rustfs-data`; healthcheck `mc ready local` →
  `curl -f http://localhost:9000/health`. Port exposure unchanged; the dev stack
  keeps a web console on `:9001`.
- **Config renamed vendor-neutral, as a deliberate hard break** (no compat
  shim — owner decision, adoption is low enough that a clean rename beats a
  deprecated alias layer):

  | Retired | Replacement |
  |---|---|
  | `MINIO_ROOT_USER`, `MINIO_ACCESS_KEY` | `S3_ACCESS_KEY` |
  | `MINIO_ROOT_PASSWORD`, `MINIO_SECRET_KEY` | `S3_SECRET_KEY` |
  | `MINIO_ENDPOINT` | `S3_ENDPOINT` |
  | `MINIO_PUBLIC_ENDPOINT` | `S3_PUBLIC_ENDPOINT` |
  | `MINIO_BUCKET` | `S3_BUCKET` |
  | `MINIO_SECURE` | `S3_SECURE` |
  | `MINIO_REGION` | `S3_REGION` |
  | `MINIO_IAM_AUTH` | `S3_IAM_AUTH` |

  The old split between `MINIO_ROOT_*` (server init) and
  `MINIO_ACCESS_KEY`/`SECRET_KEY` (backend) collapses into **one credential
  pair**, `S3_ACCESS_KEY`/`S3_SECRET_KEY`, which compose passes to both the
  `rustfs` service and the backend. Rotation is therefore
  `docker compose up -d --force-recreate rustfs backend` — RustFS reads the pair
  from its environment every start, so that *is* the whole rotation.
- **The break fails safe.** `Settings` ignores unknown env vars, so a stale
  `.env` would have been dropped silently — keys falling back to vendor defaults
  and, in the `SITE_ADDRESS`-only shape, the public endpoint falling back to
  loopback, so the default-credential guard saw nothing wrong and RustFS booted
  with `rustfsadmin` on a published port. `config._refuse_retired_minio_env` now
  **refuses to start while ANY `MINIO_*` variable is present** and prints the
  rename mapping. It runs *before* the credentials guard so an AWS install
  (`MINIO_IAM_AUTH`) is pointed at `S3_IAM_AUTH` rather than at static keys.
- **Default-credential guard extended** to cover RustFS's `rustfsadmin`
  alongside MinIO's `minioadmin`, so a carried-over install stays protected.
- **Application layer untouched.** The `minio` PyPI package stays — it is a
  generic S3 *client*, unrelated to the retired server — confined to
  `backend/storage/s3_storage.py` (renamed from `minio_storage.py`, class
  `S3Storage`). Acceptance gate was a presigned-GET round trip against RustFS in
  the exact production shape (internal endpoint ≠ public endpoint, pinned
  `us-east-1`, path-style): expiry enforced, tampered signature refused,
  `response-content-disposition` honoured.

## Why it must be documented, and why urgently

Two separate reasons, with different deadlines:

**Now, before v1.7.0 tags.** The site documents v1.6.0, and v1.6.0's compose
file pulls an image that no longer exists. Anyone following
[Quick start](https://docs.flagpost.io/start/quick-start/) today fails at
`docker compose up`. The docs cannot fix the code, but they must say so and
point at the remedy (build from `main`, or wait for v1.7.0). A broken quick
start is the worst possible first impression, and it strikes directly at the
product promise `VISION.md` and the apex page sell — *one command, no external
accounts or infrastructure*.

**At tag time.** Once v1.7.0 ships, every `MINIO_*` instruction on the site
produces a backend that refuses to boot. Published config references that
*prevent startup* are worse than merely stale.

standing between an upgrading operator and a backend that will not start. It
must carry the ordered procedure, because the order matters:

1. With the old stack still running, copy objects out — `rclone sync`, S3→S3,
   while the old server is still reachable. **Object data does not migrate
   across the server swap**; it lives in the old `minio-data` volume.
2. `docker compose down --remove-orphans`. The retired `minio` service is no
   longer in the compose file, so a plain `up -d` leaves its container running
   and holding port 9000 — and `rustfs` then cannot bind.
3. Rename the variables in `.env`, then `docker compose up -d`.
4. Sync the objects into the new `rustfs-data` server, then
   `docker volume rm <project>_minio-data`.

> The docs site should name RustFS (operators run it); the landing page need not.

# P1 — Module SDK, importing & marketplace (ADR-0040, epic #385)

## What changed

Seven commits (`b35d61a`, `679af81`, `a5bd4d0`, `f20ad43`, `a0b2825`,
`1e44abd`, `0500285`) opened the module mechanism to registry-distributed
modules — the item that sat on the *Explicitly Deferred* list since MVP.

- **Four trust tiers**, a property of the artifact declared in its manifest:
  **0** content packs (data only), **1** declarative modules (config +
  server-driven UI, no arbitrary code), **2** signed code modules (in-process,
  trust-on-signature + explicit consent), **3** sandboxed untrusted code —
  **reserved and explicitly out of scope**, still deferred. The tiers are
  designed so nothing shipping now needs a sandbox.
- **Shipped in this milestone:** Tier 0 content-pack import (#387), manifest v2
  enforced at load (#386), registry settings + artifact trust verification
  (#389), code-based resolve + install pipeline, the admin import UI
  (`/admin/marketplace`), and the module SDK CLI (#390).
  **Still open: Tier 1 (#388) and Tier 2 (#391).**
- **An open registry protocol** — a signed, static, mirrorable catalog index
  plus code-based resolution (`GET {marketplace_url}/resolve/{code}`). The
  instance takes a configurable `marketplace_url` and a trust policy, so
  `marketplace.flagpost.io` is the *default* registry, not a dependency (the
  VS Code ↔ Open VSX shape). Specs are versioned JSON Schema in
  `docs/spec/{module-manifest,catalog-index,resolve-response}.schema.json`.
- **Nothing phones home.** A registry is contacted only on explicit operator
  action (resolve / browse / install / update), sending no instance or
  competitor data. This matters for `PRIVACY.md` parity on the site.
- **Signing is orthogonal to entitlement.** The instance always verifies
  signature + digest + version compatibility, free or paid alike; a future paid
  artifact is gated only at download by an offline-verified entitlement — no
  runtime DRM, so paid content still works self-hosted and air-gapped.
- **The SDK** (`python -m sdk` from `backend/`): `keygen` (ed25519),
  `init` (scaffold a born-valid skeleton), `build` (validate + deterministic
  zip — same source, same digest, which is the content address), `sign`
  (detached signature), `validate`. It reuses the platform's own manifest model
  and verifier, so "valid here" means "installs there".

**Concrete API/catalogue deltas:**

- **2 new permissions** — `install_content_pack`, `manage_marketplace`. Both
  category **Marketplace**, scope **global**. Catalogue goes 46 → **48**.
- **2 new events** — `platform.content_pack_installed`,
  `platform.marketplace_settings_updated`. Both platform-admin: audited, a
  single bulk event rather than a per-row flood, and **not** automation
  triggers. Catalogue goes 98 → **100**.
- **New endpoints** — `POST /api/content-packs/install`,
  `GET|PUT /api/marketplace/settings`, `POST /api/marketplace/resolve`,
  `POST /api/marketplace/install`.
- **New env var** — `MARKETPLACE_ROOT_PUBLIC_KEY` (base64 raw ed25519): the
  project root signer, always trusted under the `official`/`verified`/`signed`
  policies. Empty until an official key is minted; operators can add their own
  trusted keys through marketplace settings regardless.
- **New module** — `marketplace`, required-core.

## Why it needs documenting

This is the flagship feature of the milestone and the first third-party
extension point in the product's history. Two things make it more than a
release note:

- **`dev/modules.md` is now factually wrong.** Lines 115–118 state that manifest
  keys for `settings`/`widgets` are "declared but unwired", that the frontend
  extension-slot system is "specified but not wired", and that there is **"no
  marketplace or sandboxing — modules are trusted"**. Manifest v2 formalises
  those keys and adds `trust_tier`, `capabilities`, `permissions` and
  compatibility bounds; the marketplace exists. A developer reading that page
  today is told the opposite of what the code does.
- **Authors have no entry point.** The SDK is a CLI with a signing workflow and
  an operator-side trust-setup counterpart (adding a public key under
  Admin → Marketplace → Registry & trust). None of it is discoverable from the
  site, so the feature effectively does not exist for the audience it was built
  for.

## Where it belongs

- **New page — `admin/marketplace.md`** (Administration sidebar group, after
  "Custom pages"): registry URL + trust policy, trusted keys, installing by
  code / file / URL, what the two new permissions gate, and the
  nothing-phones-home guarantee.
- **New page — `dev/module-sdk.md`** (Development group, after "Developing
  modules"): the scaffold → build → keygen → sign → publish loop, the command
  table, the `.fpmod` deterministic-zip container, signing ⟂ entitlement, and an
  explicit note that Tier 1/2 artifacts `build` and `validate` but do not yet
  `install` (#388/#391). Source: `docs/MODULE_SDK.md` in the platform repo is
  already written and close to publishable.
- **Rewrite `dev/modules.md`** lines 115–118; document manifest v2 and the four
  tiers; link both new pages. Consider mirroring the three JSON Schemas (or
  linking them) so protocol implementers have a stable reference.
- **`reference/permissions.md`** — add the Marketplace category rows to the
  catalogue table and to the built-in-roles section.
- **`reference/events.md`** — add both events to `## Platform & modules`, with
  the "audited, not an automation trigger" note the section already uses for
  `platform.imported`.
- **`reference/api.md`** — the five new endpoints.
- **`deploy/configuration.md`** — `MARKETPLACE_ROOT_PUBLIC_KEY`.
- **`dev/adrs.md`** — add 0040.
- **Apex `components/Roadmap.astro`** — see *Apex* below; this needs an owner
  decision, not a mechanical edit.

# P1 — Cross-competition skills web (ADR-0039, #364)

## What changed

A HackTheBox-style skills web: each competitor's per-category solves accumulate
across **every** event they have played, surfaced as a personal radar on their
profile (`components/skills/skills-radar.tsx`,
`components/profile/skills-card.tsx`).

- **Participant self-view only.** The PR (`41db7c4`) shipped *two* reads — the
  self view and an Administrator users×skills matrix — and **the matrix was then
  removed by owner decision** (ADR-0039 *"Amendment: admin matrix dropped"*,
  2026-09-04): the endpoint, the `compute_skill_matrix` read model, the
  `/admin/skills` page and its nav entry are all gone. The feature ships as the
  self view alone, so it no longer even touches `view_global_analytics`.
  **The docs must not promise a matrix** — the commit subject still says
  "+ admin matrix", which is a trap for anyone writing from the git log.
- **A sanctioned exception to `competition_id` scoping.** Flagpost is strictly
  tenant-scoped and cross-competition rollups sit on the deferred list. This is
  the **third** narrow carve-out, alongside `GET /api/admin/overview` and
  `GET /api/me/certificates` — and, like the latter, *the route shape is the
  authorization* (`/api/me/...` is self-scoped by construction).
- **Gating is unusual and worth stating precisely:** `skills` is a
  **required-core** module — always loaded, not one of the per-competition
  optionals — but the feature is switched **site-wide** by
  `site_settings.skills_enabled`, checked in the router guard. It cannot be a
  `competition_modules` toggle because the web spans every event.
- **API:** `GET /api/me/skills`. **New config:** `skills_cache_seconds`
  (default `30.0`).

## Why it needs documenting

It is a user-visible, competitor-facing feature with no coverage at all, and its
gating does not fit either pattern the site currently explains (required-core =
always on; optional = per-competition toggle). An operator looking for the
switch will not find it, because it is neither. It is also a genuine
differentiator against CTFd — persistent cross-event progression is not
something the comparison page can currently claim.

## Where it belongs

- **Guides** — a section in `guides/teams.md` (which covers participant-facing
  profile surfaces) or a short standalone page. Must state: self-view only,
  accumulates across every competition, site-wide switch.
- **`admin/site-settings.md`** — the `skills_enabled` switch, under
  *Operational settings* (§124).
- **`dev/architecture.md`** — add to the list of sanctioned cross-competition
  reads; this is the tenancy rule the project treats as non-negotiable, so the
  carve-out should be explicit rather than discovered.
- **`deploy/configuration.md`** — `skills_cache_seconds`.
- **`dev/adrs.md`** — add 0039 (noting the amendment).
- **Apex** — a candidate Features row and a `Comparison.astro` row at tag time.

# P1 — Boot-time baseline import (ADR-0038, #357)

## What changed

An unconfigured instance with `BOOTSTRAP_BACKUP_FILE` set imports a mounted
platform export (ADR-0016) **at startup**, provisioning owner, branding,
competitions and users declaratively instead of through the first-run wizard.

- Gated on `instance_needs_setup`, so a normal install imports **once**, while a
  reset-on-a-schedule demo re-imports on each clean boot. It marks setup
  complete itself, because `setup_completed_at` is import-immutable.
- `actor=None` — the file shares `JWT_SECRET_FILE`'s trust root, which is the
  security argument for accepting an unauthenticated declarative provision.
- **A bad, unreadable or failed import aborts startup** (`BootstrapError`)
  rather than booting an empty instance. Any import failure is wrapped, not just
  `ImportError_`, so an unexpected `IntegrityError` or object-storage error
  refuses to start *with context*.
- Multi-worker safe: serialised with a Postgres advisory lock plus a re-check,
  because `WEB_CONCURRENCY>1` would otherwise race N concurrent imports into
  unique-violation crashes and duplicate competitions. SQLite needs none.
- Suppresses the demo seed when set — a custom baseline replaces the canned
  stock accounts.

## Why it needs documenting

It is a second, parallel answer to "how does an instance get configured", and
the site currently documents exactly one (the wizard). It is the supported path
for IaC / immutable-infrastructure provisioning and for internal demo instances
that reset to a known baseline — both things operators ask for — and its failure
mode (refuse to boot) is one an operator must understand *before* they wire it
into a deployment pipeline.

## Where it belongs

- **`admin/setup.md`** — a section presenting it as the declarative alternative
  to the wizard, with the once-vs-every-boot distinction.
- **`admin/backup.md`** — the platform export is the *input*, so the two pages
  are two halves of one story.
- **`deploy/configuration.md`** — `BOOTSTRAP_BACKUP_FILE` (default off) and the
  mount.
- **`dev/adrs.md`** — add 0038.
- Platform-repo source material: `docs/INTERNAL_DEMO.md` "Option B" (new, 205
  lines) is the closest existing write-up.

# P2 — Security batch: 11 advisories, v1.7.0

Eleven security PRs merged on 2026-10-09 to 2026-10-11. The advisories
themselves are not the site's job, but several **change documented behaviour or
require operator action**, and those need to land in the normal docs rather than
only in release notes. Listed by documentation impact, not severity.

### Needs operator action

**Challenge instancing — per-instance networks (#371 + #377, GHSA-vgrr)**
Three isolation gaps. The k8s egress-deny `NetworkPolicy` allowed egress to any
host on port 53 (no `to` selector), so "deny mode" still permitted a full
bidirectional DNS-tunnel channel; it is now scoped to the cluster DNS pods.
`DeploymentUpdate.resource_limits` was `dict[str, Any]` and never inspected, so
a `challenge_edit` holder could set `{"cpu":0,"memory_mb":0,"pids":0}` — which
Docker treats as **unlimited**, disabling fork-bomb/OOM containment on the
shared host — or claim the whole ephemeral host-port range; `validate_shape` now
rejects non-positive/absurd values and caps the port count at 16. And Docker's
shared bridge gave no peer isolation, so each published-port (TCP) or `none`
instance now launches on its **own** throwaway bridge
`flagpost-net-<instance_id>`, created before the container, removed with it, and
swept by the reaper when orphaned.

> **`exposure=http` stays on the shared caddy bridge** — the ingress must share
> a network to reach instances by IP. Isolating HTTP peers is an opt-in
> follow-up, recorded as a residual in ADR-0036 + `THREAT_MODEL.md`. The docs
> should say this plainly rather than implying all peers are isolated.

**Operator action:** the egress-firewall guidance now covers **every** instance
bridge, not just `flagpost-instances` — pin Docker's `default-address-pools` and
block that whole range.
**Where:** `deploy/challenge-instances.md`, the egress section around line 137.

**Docker build context (#365, GHSA-382m)**
`backend/.dockerignore` excluded caches/`.venv`/`.env` but not `.jwt_secret`,
`.secret_key` or `*.db`. The build context is the working tree, not git, so a
`docker build` from a tree where the backend had been run natively — the
*documented* no-infra dev flow, which writes those files beside the code — baked
the live JWT signing secret, the Fernet key that decrypts every
`EncryptedString` column, and dev SQLite databases into the published image via
`COPY . .`. `.gitignore` covered them; `.dockerignore` did not, which read as
false confidence.

**Operator action worth stating:** anyone who built an image this way before
v1.7.0 should treat that image as carrying their JWT secret and Fernet key —
rotate and rebuild.
**Where:** `deploy/security.md`, plus a note in `dev/local.md` since the
documented dev flow is what creates the files.

### Changes documented behaviour

**Teams (#366, GHSA-4mmf)** — `create_team` granted the Participant role while
skipping every guard the join routes enforce: no visibility check, no invite
code, no email verification. Any authenticated user who learned a private
team-mode competition's UUID could POST a team and gain full competitor access.
`list_teams` had the same visibility gap, disclosing a private competition's
roster and its existence. Now `create_team` requires `can_see_competition` and
404s otherwise (existence stays undisclosed), `list_teams` goes through
`get_visible_competition`, and a shared `assert_email_verified_to_join` helper
applies the email-verification gate to **both** `create_team` and `join_team`
(both previously skipped it).
**Why document:** an organiser's mental model changes — in a private
competition you must join by invite code *before* you can create a team, and
email verification now blocks team creation, not just joining.
**Where:** `guides/teams.md`.

**Scoreboard freeze (#372 + #376, GHSA-r7j2)** — two distinct changes:
*(a)* the activity room broadcast `challenge.solved` / `score.adjusted` /
`achievement.awarded` pings during an active freeze; the score delta was
freeze-gated but the bare id-only ping still revealed that a team solved
challenge X at time T, letting competitors reconstruct the post-freeze solve
cadence the freeze exists to hide. Scoring-movement pings are now **suppressed
entirely while frozen** (the attempt ping, carrying no score movement, still
flows). Also, the scoreboard and activity WS authorizers checked only
`challenge_view` + existence despite claiming "same gate as REST", so a
Participant could snapshot a `not_started` board over WS; both now apply the
`#221 has_started` gate and the published+released visibility check, staff
exempt. *(b)* The frozen board valued each pre-cutoff solve at gross
`challenge_value` and dropped the per-solve multiple-choice wrong-guess penalty
the live board nets out — so a competitor who guessed wrong before solving got
the un-penalised points handed back the moment the board froze. Both frozen
recompute paths (standings **and** the points-over-time timeline, which must
agree with the table) now subtract `Submission.mc_penalty`, floored at 0.
**Why document:** what a freeze conceals is a documented promise, and frozen
totals now differ from v1.6.0 for any competition using MC penalties.
**Where:** `guides/scoreboard.md` freeze section; a note in `reference/events.md`.

**ctfcli import limits (#370, GHSA-wvjv)** — the importer read every zip member
with `zf.read()`, trusting the declared size while the route capped only the
50 MB *compressed* upload, so a ~1–2 MB DEFLATE bomb (~1000:1) could force a
multi-GB allocation and OOM the single-worker backend from the
competition-scoped Judge role. Now each member is read through a bounded reader:
**1 MiB for `challenge.yml`, 50 MiB per bundled file, 512 MiB aggregate
decompressed ceiling** (400 past it); an over-cap member is **skipped**. Bundled
filenames go through `safe_filename` for both the storage key and the stored
name, so a `..\..\evil.bat` can no longer ride into the challenge-export zip as
a traversal entry.
**Why document:** these are hard limits a legitimate importer with large
attachments will hit, and the silent skip of an over-cap member is surprising
unless stated.
**Where:** `reference/ctfcli.md` and `guides/import-export.md`.

**CSV exports (#367, GHSA-352q)** — organiser CSV exports wrote user-controlled
strings into cells unescaped, so a competitor could set a team name, display
name or free-text answer to something a spreadsheet evaluates
(`=cmd|' /C calc'!A0`), executing on the organiser's machine or silently
exfiltrating adjacent PII cells. A shared `csv_safe()` now prefixes any cell
whose text begins with `= + - @ TAB CR` with an apostrophe; server-computed
numbers and booleans pass through untouched. Applied at every export site —
registration fields, feedback responses, analytics submissions, and (in a
follow-up) the submitted-flag column of the dispute export, which was the actual
vector.
**Why document:** organisers will see leading apostrophes in exports and should
know it is deliberate.
**Where:** `guides/feedback.md`, `guides/import-export.md`.

**SSO / SAML (#374, GHSA-42m4)** — the most likely source of support tickets.
*(a)* SAML's ACS lacked the browser-binding check OIDC/OAuth2 already applied,
so an attacker could authenticate at the IdP as themselves, capture the
auto-submitting `SAMLResponse`+`RelayState`, and POST it into a victim's browser
to fixate their own session there. `saml_login` now sets an httpOnly
`sso_login_state` cookie bound to the `RelayState`, and **the ACS requires it to
match** — a single-use RelayState and `InResponseTo` only stop replay.
*(b)* `resolve_identity` linked a first-contact IdP identity to an existing
local account **by email alone**, so an attacker could pre-register
`victim@corp` (unverified, live immediately) and have the victim's real SSO
login land in the attacker's account. Linking now requires the local account's
`email_verified_at`; an unverified match is refused with
`email_unverified_conflict`. Admin-created accounts are stamped verified at
creation, so the legitimate "link my existing account" flow is unaffected.
**Why document:** *(a)* means a SAML login that does not begin at
`saml_login` in the same browser now fails — IdP-initiated flows and
cross-device logins break, and the symptom is an opaque ACS rejection.
*(b)* gives administrators a new, specific error to interpret.
**Where:** `admin/saml.md` (a troubleshooting entry for the cookie requirement
and IdP-initiated flows) and `admin/sso.md` (the linking rules and
`email_unverified_conflict`).

**Automations (#369, GHSA-x8v4)** — three authorization gaps. `list_rules`
leaked global org rules' full action configs — **webhook URLs and headers, email
templates** — to any competition-scoped `automation_view` holder (a Judge),
because it ORed globals into a competition listing while `get_rule` correctly
required a global grant; globals are now surfaced only to a caller holding
`automation_view` globally. Personal rules skipped `_authorize_trigger`, so a
competitor could subscribe a personal rule to a staff-only event about
themselves — e.g. `challenge.flag_shared_detected` — turning covert anti-cheat
detection into a self-service oracle; personal rule create/update now run the
same trigger authorization org rules do. And backup import could plant
executable automation rules on a live competition: a `manage_site_settings`
delegate with no automation grant could import the `automations` section, and
the spec had no `validate_row`, so arbitrary action/trigger JSON was persisted
and then executed. The import section gate now requires **global
`automation_create`** for the automations section, and `validate_row` re-applies
the `RuleCreate` invariant.
**Why document:** the backup-import section gate is a documented permission
matrix, and the personal-rule trigger restriction changes what a competitor can
build.
**Where:** `guides/automations.md`, `reference/automations.md`,
`admin/backup.md` (the section/permission table).

**Webhook egress (#368, GHSA-r7rp)** — the SSRF guard was
resolve-then-connect: `validate_webhook_url` resolved and checked the host, then
httpx re-resolved independently at connect time, so a DNS-rebinding host (public
on the first lookup, internal on the second) passed the check and connected
internally. `resolve_pinned_target()` now resolves and SSRF-checks once and
returns a target whose URL **is** the validated IP, carrying the original
hostname in the `Host` header and TLS SNI so routing and certificate
verification are unchanged. The response is also streamed and only the status
line consumed, so an endless chunked body can no longer grow worker memory.
ADR-0013 amended — both items moved from accepted-residual to closed.
**Where:** `reference/automations.md` (webhook action), `deploy/security.md`.

**Resource/validation hardening (#373, GHSA-4wrj)** — ticket-attachment upload
did an unbounded `file.read()` before the 2.5 MB check (the one upload route not
using `read_upload_capped`); the CRDT `note_update` relay rebroadcast any string
to every room member with no size bound, now capped at the persist ceiling;
**ticket creation is now rate-limited to 20 per 10 minutes per user**, because
each ticket unlocks fresh attachment storage and a create loop was a
storage-exhaustion vector; and the backup `pages` spec gained a `validate_row`,
since a crafted backup could publish a page skipping the slug/reserved-slug
rules and land it on the unauthenticated `GET /api/pages/{slug}`.
**Why document:** the ticket rate limit is competitor-visible.
**Where:** `guides/support.md`; `admin/backup.md`.

**Change-password + forgot-password (#375, GHSA-vv68)** — `change-password` was
the one password-taking endpoint left unthrottled, running argon2 synchronously
on the event loop at production cost (64 MiB, t=3). That made it a brute-force
oracle for anyone holding a stolen session (400-vs-204, no throttle, bypassing
the per-identifier login limiter) and an event-loop DoS (concurrent wrong-
password requests stall the default single-worker backend). Now throttled
**5 per 300s per user, before the password check** — so a correct guess past the
limit still 429s, which is what keeps it from being an oracle — and moved onto
the bounded hashing pool. A follow-up in the same PR also moved the
forgot-password token mint + mail into a background task, so the
account-exists and account-missing branches both return a uniform 204 (the
inline awaited SMTP send was a reliable account-enumeration timing oracle).
**Where:** `deploy/security.md`; optionally `admin/users-roles.md`.
