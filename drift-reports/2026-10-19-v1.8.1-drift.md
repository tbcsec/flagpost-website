> Tier 1 (declarative) and Tier 2 (signed code) modules were closed as
> not-planned (owner decision, 2026-10-13).

> Tier 1 and Tier 2 were then closed as not-planned (owner decision,

The distinction matters and the site currently collapses it:

signed-code half is not.

`flagpost-vs-ctfd.md` comparison page uses it as a competitive argument.

Six locations, all needing the same edit — drop the declarative/signed-code

# P1 — Staff live standings during a freeze (#501 → PR #504)

## What changed

The UI, the in-app copy and the Judge guide all promised staff the live board
during a freeze. The backend supported it (`?live=true` bypasses the freeze for
a `scoreboard_freeze` holder); the frontend never requested it, and the
scoreboard WebSocket room only ever carried the frozen board — so even a live
fetch would not have updated. Three symptoms fell out of the same gap: no live
view at all, a Freeze button that briefly read "Freeze" after freezing (the
freeze response is the *live* board, reporting `frozen: false`), and an
individual-mode roster showing frozen rank beside live solve counts.

The fix adds real plumbing, not just a flag:

- **A new WebSocket room type, `scoreboard_live`** (`backend/plugins/scoring/__init__.py:89`).
  It is authorized as the shared `scoreboard` room **plus** the
  `scoreboard_freeze` permission — the same grant the REST bypass checks — and
  re-broadcasts the live board on every scoring event. The shared `scoreboard`
  room keeps its freeze containment (GHSA-r7j2) untouched. A holder who loses the
  permission is evicted by the existing `realtime/eviction.py` listeners.
- **`ScoreboardOut` gains `live: bool`** (`backend/schemas/scoreboard.py`). This
  is the API-schema change: `frozen` alone could not distinguish "not frozen"
  from "frozen, and you are reading past it", which is why the freeze/unfreeze
  responses read as unfrozen. `frozen or live` is now the test for "competitors
  see a frozen board".
- With a multi-worker relay attached, **both rooms are built regardless of local
  room size**, because peers' members are not visible from one worker
  (`manager.may_have_listeners`, `backend/realtime/manager.py`).
- **Frontend:** freeze holders get a **"Show live standings"** action in the
  frozen banner. It opens on the frozen board per competition, live standings
  never stand in while the frozen view loads, an unfreeze ends the live view,
  and the Freeze control stays pending until the frozen board has loaded.
- The in-app copy is explicit about the hazard: *"Competitors still see the
  frozen board until you unfreeze it, so keep this view off shared screens."*

## Why this needs documenting

The published sentence is **factually wrong in both directions**. It told
operators of v1.7.x and v1.8.0 that a capability existed when it did not — a
judge planning an end-game freeze would have discovered mid-event that the only
way to see real standings was to unfreeze the board in front of everyone. And it
describes the new behaviour incorrectly too, because the fix is deliberately
*not* automatic: it is an opt-in view with a shared-screen warning, which is an
operational instruction, not a UI detail. Documenting "automatic" would actively
discourage the caution the feature was built with.

The new room is also the first addition to the WebSocket room inventory since
v1.4.0, and that inventory is a published integration contract.

## Where it belongs

- **`docs/src/content/docs/guides/scoreboard.md:61`** — replace *"Staff can still
  read the live board (`?live=true` — the UI does this for staff automatically)"*
  with the real flow: the frozen banner's **Show live standings** toggle, that it
  needs `scoreboard_freeze`, that it updates live, that it is per-competition and
  resets to the frozen board, that an unfreeze ends it, and the shared-screen
  warning. This is in the existing **"Freezing the board"** section, which already
  carries the freeze semantics bullet list.
- **`docs/src/content/docs/reference/api.md`, "WebSocket rooms" (~line 236)** —
  add `scoreboard_live/<competition_id>` to the room inventory, noting it is a
  snapshot room gated on `scoreboard_freeze` on top of the shared room's gates,
  and that the shared `scoreboard` room's freeze containment is unchanged.
- **`docs/src/content/docs/reference/api.md:148-154`** — the `?live=true`
  paragraph should mention that the board payload now carries `live`, and that
  `frozen or live` is the correct "competitors are seeing a frozen board" test.
- **`docs/src/content/docs/guides/scoreboard.md:35-37`** already describes the
  timeline respecting the freeze "for a `scoreboard_freeze` holder viewing the
  live board" — that line becomes correct once the toggle is documented, and
  should link to it.

# P2 — The staff ticket view rework (#503 → PR #507)

## What changed

The staff side of Support was one crowded modal; it is now a two-pane workspace.
This is the largest of the five changes (2,177 insertions) and it changes both
the API shape and a confidentiality boundary.

**Layout and navigation**
- Staff work the **queue beside the open ticket** (stacked on a phone). The open
  ticket is **in the URL (`?ticket=<id>`)**, so a ticket can be linked and shared
  with another judge, and Back returns to the queue.
- The queue gained triage signals: **Open / Resolved / All**, plus **Waiting on
  staff**, **Mine** and **Unassigned** filters with counts; each row shows who
  holds the ticket, when it last moved, and a mark when the competitor wrote last.
- The ticket gained a details panel (from, challenge, assignee, opened, last
  activity); **Assign to me** and **Resolve** are separated from the composer;
  **Conversation** and **Staff notes** are tabs rather than the notes pad sitting
  below the fold.
- The **message kind is now an explicit choice** — Reply/Answer, Internal note,
  or Clarification for everyone — as native radios, with the composer tinted and
  labelled by mode. Previously it was two checkboxes that disabled each other,
  which made it easy to send publicly what you meant as internal.
- Long unbroken text (hashes, base64, URLs) wraps instead of widening the page.
- The competitor's thread is **unchanged in behaviour** and is now
  competitor-only; the message list and send flow are shared components.

**API schema — `TicketOut` gains three fields** (`backend/schemas/ticket.py`):
- `assignee_user_id: str | None` — drives the "Mine" filter (the list previously
  carried only `assignee_name`).
- `last_activity_at: datetime | None` — the latest message **the caller can see**.
- `awaiting_staff: bool` — true when an open ticket's last *public* message came
  from its opener.

These come from **one query for every listed ticket** (`backend/utils/tickets.py`,
`_thread_stats`) instead of a count per ticket — a real efficiency change on a
busy queue.

**A confidentiality change, and this is the part that matters most**
- **`message_count` is now permission-filtered.** Internal notes count only for
  callers holding `ticket_view_internal_notes`. Previously the count included
  notes for everyone, so the number itself told a competitor that staff had
  written something they could not see.
- **Internal-note frames no longer reach the competitor's socket.**
  `ticket.message_posted` for an internal note is no longer broadcast to the
  `ticket` room (which the competitor is in) — even a body-less refresh frame,
  and the audio cue it triggers, would have disclosed that a note was written.
  Notes now ping the **staff-only `support` room** (pre-existing, not new)
  instead, which refreshes the ticket staff have open. The same applies to an
  **attachment on an internal note** (`ticket.attachment_deleted` /
  `attachment_added` handling in `backend/plugins/tickets/__init__.py`).
- Correspondingly, `TRIGGER_FIELDS["ticket.attachment_deleted"]` gained
  `is_internal` (`backend/utils/automation_catalog.py`).

## Why this needs documenting

Three independent reasons:

1. **The site's description of the staff experience is now wrong.**
   `guides/support.md:17-20` describes *"a live queue with assignment and
   resolution"* — accurate for the old modal, and a serious undersell of a
   two-pane triage workspace with filters, waiting-on-staff signals and
   shareable per-ticket URLs. The shareable link in particular is a workflow
   capability organisers will not discover on their own.
2. **The internal-note change is a privacy fix and should be stated as one.**
   The site already makes a firm promise at `guides/support.md:19-20`: internal
   notes are *"visible only to staff holding `ticket_view_internal_notes` — never
   to the ticket's opener."* Until this commit that promise had two side
   channels — the message count and the WebSocket refresh frame plus its chime.
   The guide should say the boundary now covers counts and real-time frames, not
   just note bodies. Operators who handle disputes under that promise need to
   know which version of it they are running.
3. **The audio-cue documentation is now incomplete.** `guides/support.md:25-27`
   calls the ticket chime *"the only sound in the platform"* and says a reply
   cues *"whichever side didn't just post"*. An internal note now deliberately
   cues neither side's competitor socket. That is exactly the kind of detail the
   guide exists to pin down.

## Where it belongs

- **`docs/src/content/docs/guides/support.md`, "Support tickets" (lines 10-33)** —
  rewrite the **For staff** bullet into a short subsection covering the queue
  (filters, counts, assignee, last activity, waiting-on-staff), the two-pane
  layout with the phone fallback, the `?ticket=` shareable link, the details
  panel, the Conversation / Staff notes tabs, and the explicit Reply / Internal
  note / Clarification mode selector. Keep the competitor bullet as it is and say
  it is unchanged.
- **Same file, the internal-notes promise (lines 18-20)** — extend it: counts and
  real-time frames are now filtered too, so neither the message count nor a chime
  reveals a note. Worth a short note that this tightened after v1.8.0.
- **Same file, the audio cue bullet (lines 25-27)** — note the internal-note
  exception.
- **`docs/src/content/docs/reference/api.md`, around the ticket routes (~line 193)** —
  document `assignee_user_id`, `last_activity_at` and `awaiting_staff` on the
  ticket list, and **flag the `message_count` semantic change explicitly** as a
  behavioural break for any integration reading it: the same ticket now reports
  different counts to different callers. The site does not currently enumerate
  ticket response fields, so this may be one new paragraph rather than a table.
- **`docs/src/content/docs/reference/api.md`, "WebSocket rooms"** — note that
  internal-note activity is delivered on the competition-scoped staff `support`
  room rather than the per-ticket `ticket` room.
- **`docs/src/content/docs/reference/automations.md`** — the reference does *not*
  enumerate per-trigger payload fields today, so `is_internal` needs no edit.
  Recorded here only so the next pass does not treat it as missed.

# P3 — Competition modules as tiles (#502 → PR #506)

## What changed

Settings → Modules was two plain lists headed by machine ids and versions, with
nothing saying what a module does. It is now a grid of tiles:

- Each tile carries the module's **glyph**, a **plain-language name and
  description written as UI copy** (a `moduleCatalog` block in
  `messages/en.json`, falling back to the manifest text for an unknown module),
  and an **on/off switch**. Optional modules come first; required-core modules sit
  in a folded group below. The id and version moved into the tile's tooltip, still
  reachable for support.
- **AI, Challenge Instances and the Code Judge now say "Needs site setup"** until
  an administrator switches them on site-wide — *"Needs site setup: an
  administrator has to configure this before it does anything."*
- The **New competition dialog uses the same tiles**.
- The sidebar's inline glyphs moved into a shared `module-icons` catalog so a
  module looks identical in the sidebar and on its tile; a new `Switch` primitive
  was added.

**API schema changes** (`backend/schemas/module.py`, `backend/routers/modules.py`):
- `ModuleStateOut` gains **`description: str`** (the manifest one-liner, exposed
  for the first time — the UI writes its own copy and falls back to this) and
  **`needs_setup: bool`**.
- `ModuleCatalogEntry` gains **`needs_setup: bool`**.
- `GET /api/modules` now resolves the three site-wide master switches
  (`AiSettings`, `InstanceSettings`, `JudgeSettings`) to compute `needs_setup`,
  so the endpoint took a DB dependency it did not have before.

## Why this needs documenting

The **"Needs site setup"** state is the documentation-worthy part. The site
already explains, at `guides/competitions.md:138-141`, that AI, Instances and the
Code Judge sit behind a site-wide switch — but an organiser previously had to
read that sentence to understand why flipping a module on did nothing. The product
now tells them in place, and the docs should match the words they will see on
screen, because *"Needs site setup"* is the string they will search for.

The API fields matter for a second reason: `needs_setup` is **derived
site-wide state exposed on a competition-scoped read**, which is unusual enough
in this codebase that an integrator reading the module inventory should know it
reflects an administrator's site configuration, not this competition's toggle.

`guides/competitions.md:144` — *"Required-core modules are listed but locked
on"* — is also now imprecise: they are collapsed into a folded "always on" group,
not listed inline.

## Where it belongs

- **`docs/src/content/docs/guides/competitions.md`, "Modules" (lines 131-147)** —
  describe the tile grid, the per-module descriptions, the folded always-on
  group, and the tooltip as where id and version now live. Tie the existing
  site-wide-switch sentence to the **"Needs site setup"** badge by name.
- **Same file, "Creating a competition" (lines 25-28)** — the picker is now the
  same tiles, and it shows `needs_setup` too, so an organiser sees before the
  competition exists that a module will need an administrator.
- **`docs/src/content/docs/dev/modules.md` (~line 37)** — `GET /api/modules` now
  returns `description` and `needs_setup`. The manifest's `description` is now
  **surfaced through the API**, which changes the authoring guidance: it is still
  developer-facing, it is the fallback copy for a module the UI does not know, and
  the judge manifest's "container endpoint" phrasing is the cautionary example
  the issue itself cited. Worth one line telling module authors their manifest
  description can now reach an organiser's screen.
- **`docs/src/content/docs/reference/api.md:95`** — the `GET /api/modules`
  sentence should mention the two new fields.
- **`docs/src/content/docs/admin/site-settings.md`** — where the AI / Instances /
  Code Judge master switches are documented, note that leaving one off now shows
  organisers "Needs site setup" on the module tile.

# P4 — A route into later competitions after the first join (#505)

## What changed

Once a competitor joined their first competition the **Lobby link vanished**, and
picking an unjoined public competition in the switcher landed them on pages the
server refused. Frontend-only, but it changes the competitor's mental model of
how they move between events.

- A competition the viewer has **not joined now shows a join panel in place of
  its pages** — the lobby's self-serve flow (fields, rules, join). Nothing
  competition-scoped is fetched or opened for it: no modules, no activity room,
  no announcements, no assistant, no certificate watcher. A competition page now
  waits for permissions and the competition list rather than rendering before it
  knows.
- The **switcher is its own component** and groups **"Your competitions"** apart
  from **"Open to join"**, with a **Join** button beside it leading to the lobby
  for invite codes. It is hidden from anyone already in every competition. Its
  default selection prefers a joined competition once permissions load, and still
  picks one if permissions fail.
- After **any** join the competition is listed and made active at once (a private
  one joined by code was previously not listed until a refetch), and the join
  stays pending until permissions confirm membership.
- **The lobby now serves members too:** joined competitions read **"Joined"**
  with an **Open** button, under a subtitle about joining another.
- The public join flow moved out of the lobby into a shared, tested hook.

## Why this needs documenting

This is the one change with **no real home on the site today**. "Lobby" appears
exactly three times across the whole docs tree, all in passing
(`guides/competitions.md:21`, `:41`, `:157`), and always from the organiser's
side — *"public competitions appear in the lobby"*. There is no description
anywhere of how a competitor actually finds and joins a second event.

That gap is why the bug survived: the behaviour nobody documented was also the
behaviour nobody noticed was broken. A multi-event organiser — exactly the
audience for a platform with a competition switcher — would have had competitors
unable to reach the next event without being sent a direct link, and nothing on
the site would have told either party that was unexpected.

## Where it belongs

- **`docs/src/content/docs/guides/competitions.md`, "Joining" (lines 43-45)** —
  extend the organiser-side joining bullet with what the competitor sees: the
  lobby lists public competitions and marks the ones they have joined, the
  switcher separates **Your competitions** from **Open to join**, and selecting
  an unjoined public competition offers the join panel in place of its pages
  rather than failing.
- **`docs/src/content/docs/start/concepts.md`** — the better long-term home. A
  short "moving between competitions" paragraph belongs with the tenancy concept,
  since the switcher *is* how the `competition_id` root surfaces to a competitor.
- **`docs/src/content/docs/guides/host-a-ctf.md`** — worth one line for organisers
  running back-to-back events, that returning competitors reach the next one
  through the lobby or the switcher without a fresh invite.

# P5 — Ticket notifications open the ticket (#508 → PR #509)

**The only issue in the `v1.8.1` milestone.**

## What changed

Every ticket notification linked to the bare Support page, so after clicking one
you still had to find the ticket.

- Each ticket notification (**new ticket, assigned, reply, resolved**) now links
  to **`/support?ticket=<id>`**.
- **Activating a notification in the bell switches to its competition first**, so
  a ticket from another competition opens instead of coming up "not available".
  The same-origin link guard moved into a tested helper
  (`frontend/src/lib/notification-link.ts`).
- The **competitor's** Support page keeps its open ticket in the URL too, so the
  link opens the thread for them as it does for staff.
- `backend/models/notification.py` — the `link` column's documented example
  changed from a competition-scoped path
  (`/competitions/<id>/support?ticket=<id>`) to a **bare `/support?ticket=<id>`**,
  with the client resolving the competition from its store and switching first.

## Why this needs documenting

The link format is a **stored, competition-agnostic deep link**, which is the
non-obvious part: a notification row no longer encodes its own competition, and
anything reading `Notification.link` must pair it with `competition_id` to
resolve it. That is a contract worth stating once, because the `notify`
automation action writes notifications and the site documents that action.

The user-facing half is smaller but real: the site's notifications section
(`guides/support.md:113-125`) describes the bell as collecting *"ticket
activity"* with read state and delivery hints, and says nothing about where
activating one takes you — now a meaningfully better answer, and one that works
across competitions.

## Where it belongs

- **`docs/src/content/docs/guides/support.md`, "Notifications" (lines 113-117)** —
  one sentence: activating a ticket notification opens that ticket, switching
  competition first if it belongs to another.
- **`docs/src/content/docs/reference/api.md`** — where notifications and the
  per-user WebSocket room are covered, note the `link` shape
  (`/support?ticket=<id>`) and that it resolves against the notification's
  `competition_id` rather than carrying the competition in the path.
- **`docs/src/content/docs/guides/automations.md`** — the `notify` action's
  description should mention that a notification can carry an in-app deep link
  resolved this way.
